## 3. 手工验收步骤

启动：`cd frontend && npm run dev`（前端 5173/81 端口按项目配置），后端按既有方式启动。

### 场景 A：默认与基本筛选（对应 US1）

1. 进入「本体设计 → 需求汇总」。
2. **期望**：标题行右侧出现下拉，显示「全部」；表格行数与该本体下全部需求文档数一致。
3. 展开下拉：**期望** 首项「全部」，随后为本体下实际存在的版本号，**降序**排列，无多余项。
4. 选 `v1.9`：**期望** 只剩 `v1.9` 的行；切网络面板确认**没有新请求**（本地过滤）；用 Performance 面板记录"点击到表格完成重绘"的耗时，应 ≤200ms（SC-003 的人工观测口径，记入验收记录）。
5. 选「全部」：**期望** 恢复全部行。

### 场景 B：自然排序（对应 FR-005）

1. 造 `v1.9`、`v1.10`、`v2.0` 三份文档。
2. 展开下拉：**期望** 顺序为 `v2.0 → v1.10 → v1.9`（不是 `v1.9` 在前）。

### 场景 C：空版本不丢失（对应 FR-004 / SC-006）

1. 让某条需求文档的所属线程 `version` 为空串。
2. 展开下拉：**期望** 出现「未填写版本」，位于**最后**。
3. 选中它：**期望** 只显示版本号为空的文档，条数与实际一致。

### 场景 D：删除后回落（对应 FR-009 / SC-004）

1. 选一个只有 1 条文档的版本。
2. 删除该文档并确认。
3. **期望**：提示「当前版本已无需求文档，已显示全部」；下拉自动变回「全部」；表格显示其余文档；下拉中该版本号消失。

### 场景 E：返回详情保持筛选（对应 FR-010）

1. 选某版本，点「查看」进入详情，再返回。
2. **期望** 下拉仍是该版本，表格仍只显示该版本。

### 场景 F：上下文重置（对应 FR-011）

1. 选某版本后，切换到另一个场景/本体再回到需求汇总。
2. **期望** 下拉回到「全部」。

### 场景 G：无障碍（对应章程 IV）

1. 用 Tab 聚焦下拉 → Enter 展开 → 方向键移动 → Enter 确认。
2. **期望** 全程可完成筛选，无需鼠标；读屏播报含「按版本号筛选」。

### 场景 H：零回归（对应 FR-012 / SC-005）

1. 不做任何筛选，对比改动前后的表格：列顺序、列宽、排序、状态标签、操作按钮完全一致。
2. 「本体生成」列的已生成/未生成状态在筛选前后对同一文档保持不变。

## 4. 失败判定（出现任一条即视为未完成）

- 下拉里出现当前没有文档的版本号。
- 空版本文档在任何筛选下都查不到。
- `v1.9` 排在 `v1.10` 之前。
- 删除当前版本最后一条后停在空表格且无提示。
- 切换筛选时发起了新的列表请求。
- 未筛选时的行数/列/排序与改动前不一致。
- 全量 `vitest run` 出现任何失败，或 eslint 新增 error。

---

## 5. 回滚

本特性只改前端 2 个源文件 + 1 处测试配置，无数据迁移、无接口变更。回滚方式：还原 `RequirementSummary.tsx`、删除 `requirement-version-filter.ts` 及其测试、移除 `vitest.config.ts` 中的一行 include 即可，不影响任何既有数据。
