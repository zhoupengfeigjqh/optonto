# 功能规范：core-backend 分层重构与 business-backend 并发一致性加固

**特性分支**: `002-backend-layering-consistency`

**创建日期**: 2026-09-28

**状态**: 草稿

**输入**: 用户描述："core-backend 分层重构与 business-backend 并发一致性加固"

## 用户场景与测试 *（必填）*

### 用户故事 1 - 并发下业务写操作不丢状态、库存账实一致（优先级：P1）

作为业务系统的使用者，我希望并发发起「取消采购单 / 确认入库」时不会互相覆盖状态，
且确认入库后库存数量被正确回写，这样业务数据不会出现「状态被覆盖」和「入库了但库存没变」的错误。

**优先级理由**：这是**数据正确性**问题（章程 VI），会造成静默的数据错误，优先级最高。

**独立验证**：对同一采购单并发调用 cancel 与 receive，检查最终状态唯一且符合预期；
调用 receive 后核对 inventory 的 `cumulative_stock_quantity` / `pending_receipt_quantity` 已按到货数量更新。

**验收场景**：

1. **Given** 一条「待入库」采购单，**When** 并发两次「取消」，**Then** 只有一次生效，另一次返回冲突错误（HTTP 409），最终状态为「已取消」且不重复处理。
2. **Given** 一条「待入库」采购单，**When** 并发执行「取消」与「入库」，**Then** 至多一个成功，另一个收到冲突错误；最终状态唯一，无部分提交。
3. **Given** 一条已入库采购单，**When** 再次调用「入库」，**Then** 返回幂等提示且库存**不重复累加**。
4. **Given** 一次成功入库，**When** 查询库存，**Then** 入库数量已回写（累计入库增加、待入库减少），事务内要么全成要么全不成。

---

### 用户故事 2 - core-backend 恢复分层，路由层不再直接读写文件（优先级：P2）

作为后端维护者，我希望路由层只做「参数校验 + 调用业务层」，文件读写收敛到数据访问层，
这样改存储实现时不必翻遍路由，也不会出现同一份文件在不同路由里各写一遍的情况。

**优先级理由**：章程 II 的硬约束（分层、禁止跨层）；属结构治理，不直接产生功能变更，故排在 P1 之后。

**独立验证**：在路由文件中搜索 `open(`、`read_text`、`write_text`、`shutil.rmtree`，结果应为 0；
业务层文件不出现 `fastapi.Request` / `HTTPException` 依赖。

**验收场景**：

1. **Given** 重构后的路由层，**When** 静态检索文件 I/O 调用，**Then** 路由层为 0 处（全部下沉到数据访问层）。
2. **Given** 重构后的业务层，**When** 静态检索 HTTP 框架类型，**Then** 业务层不依赖 HTTP 请求/响应对象。
3. **Given** 同样的 API 调用，**When** 重构前后对比响应，**Then** 行为与错误契约一致（无回归）。

---

### 用户故事 3 - 接口文档可查阅（优先级：P3）

作为前后端协作的开发者，我希望 Java 业务后端提供可浏览的接口文档，
这样新增或调整接口时前后端能对齐契约，不必靠读代码猜。

**优先级理由**：章程 VI 要求「所有端点必须有接口文档」；属协作效率问题，故排在 P3。

**独立验证**：启动服务后访问文档端点，能看到全部 REST 端点的路径、方法、请求与响应结构。

**验收场景**：

1. **Given** 业务后端已启动，**When** 访问文档端点，**Then** 返回可交互的 OpenAPI 文档页面，且包含全部端点。
2. **Given** 新增一个端点，**When** 重新访问文档，**Then** 新端点自动出现在文档中。

---

### 边界情况

- **乐观锁冲突**：并发热点数据（同一采购单）冲突率上升时，必须返回明确的冲突语义而非静默覆盖。
- **幂等边界**：重复取消 / 重复入库必须幂等，不得重复扣减或累加库存。
- **历史数据**：加锁字段/库存字段为新增列时，存量行必须有合理默认值，迁移脚本需可重复执行或明确说明一次性。
- **跨表一致性**：入库需同时改采购单状态与库存；任一步失败必须整体回滚。
- **重构回归**：分层重构期间接口对外行为（含错误契约）必须保持不变。

## 需求 *（必填）*

### 功能需求

- **FR-001**: 涉及状态变更的操作 MUST 具备并发控制机制，冲突时 MUST 返回 409 且错误体遵循统一契约。
- **FR-002**: 「取消 / 入库」MUST 幂等；重复请求 MUST NOT 重复改变业务状态或库存数量。
- **FR-003**: 确认入库 MUST 在**同一事务**内回写采购单状态与库存数量，MUST NOT 部分提交。
- **FR-004**: 库存回写的数量口径 MUST 明确（待入库、累计入库、可用库存三者的增减规则）。
- **FR-005**: core-backend MUST 引入独立数据访问层；路由层 MUST NOT 直接进行文件 I/O。
- **FR-006**: core-backend 业务层 MUST NOT 依赖 HTTP 框架类型（`Request` / `HTTPException`）。
- **FR-007**: core-backend 重构 MUST 保持既有 API 路径、请求/响应结构与统一错误契约不变。
- **FR-008**: business-backend MUST 提供可访问的接口文档，覆盖全部 REST 端点。
- **FR-009**: 数据库结构变更 MUST 提供迁移脚本，并在脚本中说明适用场景与一次性/幂等属性。
- **FR-010**: 超过 500 行的后端文件 MUST 拆分至 500 行以内。

### 关键实体

- **采购单（purchase_record）**：含业务单号、状态、到货数量；需并发控制字段。
- **库存（inventory）**：与原材料 1:1，含待入库数量、累计入库数量、可用库存、已消耗数量。
- **数据访问层（core-backend）**：封装 `.data` 文件读写的唯一入口，供业务层调用。
- **接口文档**：由代码注解生成的 OpenAPI 描述，随端点自动更新。

## 成功标准 *（必填）*

### 可衡量结果

- **SC-001**: 对同一采购单并发执行「取消/入库」20 次，最终状态唯一、无部分提交、无数据异常（0 例状态丢失）。
- **SC-002**: 一次入库后库存对账通过：累计入库增量 = 到货数量，待入库减量一致，重复入库增量为 0。
- **SC-003**: core-backend 路由层文件 I/O 调用数为 0；业务层 HTTP 框架依赖数为 0。
- **SC-004**: 重构前后同一组 API 请求的响应与错误契约完全一致（回归用例全绿）。
- **SC-005**: 业务后端文档端点返回 200 且包含全部端点。
- **SC-006**: 后端源文件行数 >500 的数量为 0。

## 假设

- 部署形态为单实例（无分布式锁需求），并发控制可用数据库层面的乐观锁/唯一约束实现。
- 数据库为 MySQL 8，具备事务与唯一索引能力。
- 业务后端为模拟业务系统，允许调整其数据模型与迁移脚本。
- core-backend 的 `.data` 为文件型存储，重构目标是收敛读写入口而非替换存储引擎。
- 重构期间接口契约不变，前端与 MCP 服务无需同步改动。
