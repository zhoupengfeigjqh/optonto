# 决策记录：数据引擎执行服务零工具化（方案 B）

- 日期：2026-10-19
- 状态：已采纳（用户拍板）
- 影响契约：`specs/contracts/mcp-tools.md` §1 / §2 / §7 / §8 / §9.2 / §11

## 背景

数据引擎执行服务（8005）此前同时承担两件事：

1. 行为的**执行底座**（`/call-behavior`、`/call-engine`，自建发布与设计器测试都转发到这里）；
2. 行为的**MCP 工具发布面**（`/mcp`，把全平台所有已就绪行为发布为工具，仅供内网 Agent 挂载）。

2026-10-04 起它从「内置恒全选」降级为「预置服务」，2026-10-19 前的实际部署中已没有 Agent
挂载它——行为工具全部来自自建发布容器。

## 问题

- **两套授权答案**：全量内网挂载（无鉴权、全本体）与自建发布（按本体切片、带令牌、发布即冻结）
  同时存在，"谁能调用哪些行为"没有唯一答案。
- **同名工具重复**：同一行为可被 8005 与自建发布同时发布，Agent 目录里出现同名工具，
  发现顺序决定路由，且两处实现（`behavior_tools` 与 core `compile_tools`）编译同一份 schema。
- **规划与挂载不一致的隐患**：只要 8005 不在配置里，规划面（按"已映射就绪"）就会承诺
  一些没有挂载点的行为。

## 决定

- 8005 保留为**零工具执行底座**（`transport=none`），只提供 REST 执行端点；
- 行为工具的唯一出口 = **自建发布**；
- 行为"可规划"的判据从"已映射就绪"改为**实际挂载目录**（`FunctionCatalogView.behaviorNames`）；
- 查询面 `listOntoBehaviors` 改为「已就绪 ∩ 已发布」；
- 存量 MCP 配置中指向 8005 的条目**直接丢弃**（按 host:port 判定，含更名前容器名）。
- 8005 的 `behavior_tools.py` 收缩为 `behavior_index.py`（归属校验 + 未就绪区分），
  删除工具 schema 编译——唯一实现留在 `mcp-shared/tool_contract.py`，由 core 发布面使用。

## 后果

**收益**

- "发布即授权"成为结构事实（不再依赖配置约定）；
- 消除同名工具与重复 schema 编译；
- 8005/8006 两个执行底座口径一致，拓扑护栏可直接锁定（`TRANSPORT_NONE` + 无 `list_tools`/`call_tool`）。

**代价（明确接受）**

- 行为必须先发布才能被 Agent 使用；发布是冻结快照，改参数需删除重建；
- 新增行为入口依赖 docker.sock（无 Docker 的本地/CI 环境不可用行为）；
- 多本体对话需要多个发布容器同时启用；
- 上线前必须校验「已就绪 ⊆ 已发布」，否则该部分行为上线后不可规划。

## 上线顺序与回滚

1. agent-backend（配置迁移 + 规划判据切目录）——此时 8005 工具面仍在，但已无 Agent 连接；
2. core-backend / frontend（护栏与文案，无功能性变更）；
3. 8005 切 `none` 并重建容器。

回滚：还原 `data-engine-executor/server.py` 即恢复工具面；agent 侧需手动补回 MCP 配置条目
（或整提交回滚）。
