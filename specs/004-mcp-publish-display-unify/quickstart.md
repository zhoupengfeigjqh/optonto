# 验证指南：MCP 发布页的配置展示与卡片结构统一

**特性**: [spec.md](./spec.md) | **计划**: [plan.md](./plan.md) | **日期**: 2026-10-19

本文只给**可执行的验证步骤与预期结果**，不重复契约细节（见 `contracts/`）与实体定义（见 `data-model.md`）。

## 0. 前置条件

- 仓库根可用的 `docker-compose.yml`（拓扑护栏的事实源）；
- 前端依赖已安装（`frontend/node_modules` 存在）；
- core-backend 的 Python 依赖可用（能 import `fastapi`、`yaml`）；
- 需要人工验证时：`optonto-core-backend`、`optonto-frontend`、`optonto-nginx`、三个对外 MCP 服务（本体查询 / 公共函数 / 业务系统）已启动。

## 1. 自动化门禁（每次改动必跑）

```bash
# 前端：单测 + 静态检查
cd frontend
npm test
npm run lint

# 后端：自建发布接口 + 跨仓拓扑护栏
cd ../core-backend
python -m unittest tests.test_mcp_publish -v
python -m unittest tests.test_service_topology_consistency -v
```

**通过判据**：全部用例通过、lint 无新增告警；拓扑护栏中下列断言必须仍然绿：

- `test_白名单键与前端卡片键一一对应`
- `test_前端对外端点必须有对应宿主端口`
- `test_前端内网端点不得对外发布端口`
- `test_客户端配置片段的type取客户端认的取值`
- `test_公共函数迁移后旧端点只允许出现在归位说明里`
- 新增：`test_三个对外固定服务的片段都含两段地址`

## 2. 需求 1 验证：固定发布「查看配置」两段式

### 2.1 界面步骤

1. 打开 `http://<宿主>:81/design/<ontology_id>` → 「MCP发布」→「固定发布」；
2. 依次点击三张对外卡片的「查看配置」。

**预期**

| 卡片 | 第一段 | 第二段 | 不得出现 |
|---|---|---|---|
| 本体查询 MCP 服务 | `http://<宿主>:8002/mcp` | `http://optonto-ontology-query-mcp:8002/mcp` | 管理字段 |
| 公共函数 MCP 服务 | `http://<宿主>:8007/mcp` | `http://optonto-common-function-mcp:8007/mcp` | 管理字段 |
| 业务系统 MCP | `http://<宿主>:8004/mcp` | `http://optonto-business-mcp:8004/mcp` | `enabled` / `business_data` / `allowed_tools` |

三张弹窗的 JSON **结构一致**（`mcpServers` → 服务标识 → `type` + `url`），仅服务标识、端口、说明文案不同；两段都有明确的用途标签。

### 2.2 粘贴近端验证（关键）

| 段 | 操作 | 预期 |
|---|---|---|
| 第一段 | 粘进宿主上的 Claude Code / VS Code 的 MCP 配置并重连 | 能列出该服务工具（本体查询 8 个 / 公共函数 7 个 / 业务系统 8 个） |
| 第二段 | 平台「MCP 配置」页 →「粘贴配置」→ 保存 | 条目落库，URL 为容器名；探针「测试连接」成功并列出工具 |

> 反向验证（防止地址混用）：把第一段粘进平台「MCP 配置」→ 探针应失败（`localhost` 在 Agent 容器里指向它自己）；把第二段粘进宿主客户端 → 也应失败（容器名在宿主不可解析）。失败是**预期**，说明两段用途标注必须显眼。

### 2.3 零工具底座

点击「数据引擎执行服务」「本体函数执行服务」的「查看配置」：

- 预期：**不出现** `mcpServers` 片段；只出现内网端点说明（`internal: true` + endpoint + 可用端点列表）；
- 数据引擎执行服务不得出现 `8005/mcp` 之类已不存在的协议端点。

### 2.4 业务系统未登记场景

临时把 `config/mcp-config.json` 中业务系统条目移除（或改名）后重载页面，再点「查看配置」：

- 预期：仍给出两段片段（无 `headers`），并提示“请先在「MCP 配置」页新增该服务”；
- 不得出现空白弹窗或整块报错。

## 3. 需求 2 验证：自建发布卡片对齐 + 查看工具

### 3.1 结构对齐

1. 在「固定发布」与「自建发布」之间来回切换；
2. 并排比较两类卡片。

**预期信息层级一致**：标题 + 标签 → 状态位（点 + 文本）→ 端点 → 传输模式 → 可用工具（数量 + 查看入口）→ 说明/领域信息 → 按钮组。

**自建发布必须仍可见**：发布类型与已选工具名、所属本体、访问令牌、依赖的执行服务、`工具清单为发布时快照`提示、删除按钮。

**状态口径**：`检查中… / 运行中 / 已停止` 两块一致；自建发布额外出现 `容器缺失`（容器被外部删除时），且与 `已停止` 可区分。

### 3.2 查看工具

1. 选一条有工具的自建发布 → 点「查看工具」；
2. 展开任一工具的「N 个参数」。

**预期**

- 弹窗列出全部工具，条数与卡片「N 个」一致；
- 每条可展开参数（名称 / 类型 / 必填标记 / 描述）；
- 弹窗内可见“发布时快照，修改本体后需重新发布才会更新”；
- 该发布容器**已停止**时，仍能查看（数据来自发布记录，不依赖容器）。

### 3.3 失败与空态

| 场景 | 操作 | 预期 |
|---|---|---|
| 发布记录不存在 | 直接请求已删除的发布名 | 错误提示含“不存在”，**不打开**空清单弹窗 |
| 后端不可用 | 停掉 core-backend 后点「查看工具」 | 错误提示含网络/服务原因；不显示“0 个工具” |
| 空快照 | 构造 `tools: []` 的条目（测试环境） | 弹窗显示“0 个工具（发布时未勾选任何工具）”，不报错 |

## 4. 接口级验证（不经界面）

```bash
# 列出自建发布，取一个 name
curl -s http://localhost:8001/api/mcp/published | head -40

# 工具快照（替换 <name>）
curl -s http://localhost:8001/api/mcp/published/<name>/tools

# 不存在的发布 → 应为 404，且响应体含“不存在”
curl -s -o /dev/stderr -w "%{http_code}\n" http://localhost:8001/api/mcp/published/no-such-svc/tools
```

**判据**

- 成功：`name` / `kind` / `ontology_name` / `tools` 四字段齐备；`tools.length` 与列表接口的 `tool_count` 相等；
- 404：`{"code":404,"message":"自建发布不存在: no-such-svc",…}`；
- 响应中**不含**容器运行态字段（本端点不探测容器）。

## 5. 回归范围（本次不应被破坏）

| 检查 | 命令/操作 | 预期 |
|---|---|---|
| 固定服务启停 | 卡片「停止 / 启动」 | 状态与影响面确认框照常；`/api/mcp/{service}/status` 正常 |
| 自建发布创建/停止/删除 | 「+ 新建发布」全流程 | 行为不变；工具数量与勾选一致 |

| 零工具底座 | 数据引擎执行服务卡片 | 显示“只提供内部执行端点”，无「查看工具」入口 |
