# 功能规范：MCP 发布页的配置展示与卡片结构统一

**特性分支**: `004-mcp-publish-display-unify`

**创建日期**: 2026-10-19

**状态**: 草稿（待澄清/待规划）

**输入**: 用户提出两项需求——① MCP 发布·固定发布中，本体查询 MCP 服务、公共函数 MCP 服务、业务系统 MCP 的「查看配置」统一为「宿主地址 + 容器内地址」两段式，结构对齐自建发布（`{mcpServers: …}`），业务系统 MCP 的现有内容需重写；② MCP 发布·自建发布的卡片展示内容结构对齐固定发布卡片，并补「查看工具」能力。全部文档使用中文。

## 用户场景与测试 *（必填）*

### 用户故事 1 - 固定发布的「查看配置」给出可直接粘贴的两段式片段（优先级：P1）

作为要把平台能力接到外部 AI 客户端的开发者，我希望在本体查询 MCP 服务、公共函数 MCP 服务、业务系统 MCP 三张卡片上点「查看配置」时，都拿到同样结构的两段配置——第一段用宿主地址给平台外的客户端，第二段用容器内地址给平台自己的 Agent——这样我不必先失败一次才知道该复制哪一段。

**优先级理由**：当前三张卡片里只有两张遵循该范式，业务系统 MCP 展示的是平台内部存储条目（含启用状态、业务数据标记等无法被任何 MCP 客户端识别的字段），且地址是容器名（外部客户端解析不到）。这是现网正在发生的可用性缺陷，修复收益最直接、影响面最小。

**独立验证**：分别打开三张卡片的「查看配置」，比对两段的地址形态与结构；把第一段粘进外部 MCP 客户端、第二段粘进平台「MCP 配置」页，均应能直接连接并列出工具，无需手工改写字段。

**验收场景**：

1. **Given** 已部署环境（宿主端口 8002/8007/8004 可达），**When** 打开本体查询 MCP 服务的「查看配置」，**Then** 弹窗给出两段：第一段为宿主地址的连接片段（可粘贴进外部客户端），第二段为容器内地址的连接片段（可粘贴进平台 MCP 配置页），两段结构完全一致。
2. **Given** 同上，**When** 打开公共函数 MCP 服务的「查看配置」，**Then** 结构与本体查询服务逐字段一致（仅服务标识、端口、说明文案不同）。
3. **Given** 同上，**When** 打开业务系统 MCP 服务的「查看配置」，**Then** 给出同结构两段片段，且片段中不再出现平台管理字段（启用状态、业务数据标记、工具范围等）。
4. **Given** 业务系统 MCP 尚未在平台「MCP 配置」页登记，**When** 打开其「查看配置」，**Then** 仍给出参考片段，并明确提示需先在配置页新增该服务。
5. **Given** 某固定服务在配置页登记了鉴权请求头，**When** 打开其「查看配置」，**Then** 片段携带同样的请求头；**Given** 未登记，**Then** 片段不得凭空生成请求头。
6. **Given** 两个内网执行底座（数据引擎执行服务、本体函数执行服务，均为零工具、无协议端点），**When** 打开其「查看配置」，**Then** 不生成任何客户端连接片段，只说明内网执行端点与调用入口，且不出现宿主地址。

### 用户故事 2 - 自建发布卡片与固定发布卡片采用同一信息结构（优先级：P2）

作为在「MCP 发布」页管理服务的运维者，我希望两块区域的卡片按同一套信息层级展示——服务名、运行状态、端点、传输模式、可用工具数量与查看入口、角色说明、操作按钮——这样我在两块之间切换时不需要重新寻找同一个信息。

**优先级理由**：两块在页面上同权并列，卡片结构不一致会让用户反复确认“这块是不是缺了状态/缺了工具”。该项是纯展示重构，不改变任何行为，可在 P1 之后独立交付。

**独立验证**：把固定发布与自建发布各一张卡片并排比对，逐项核对信息项与顺序；自建发布的必要领域信息（发布类型与工具名、所属本体、访问令牌、依赖服务）均未丢失。

**验收场景**：

1. **Given** 两块视图各有若干卡片，**When** 并排查看，**Then** 两张卡片的信息项集合与排列顺序一致（服务名 → 运行状态 → 端点 → 传输模式 → 可用工具 → 角色说明 → 操作按钮）。
2. **Given** 一张自建发布卡片，**When** 查看其内容，**Then** 仍能看到发布类型与已选工具、所属本体、访问令牌、依赖的执行服务与「工具清单为发布时快照」提示。
3. **Given** 固定发布卡片显示运行中/已停止状态，**When** 查看自建发布卡片，**Then** 状态表达采用同一套视觉与文案口径；自建发布特有的「容器缺失」态有明确区分。
4. **Given** 任一张卡片，**When** 在常见桌面视口下浏览，**Then** 信息完整可读，按钮不换行错位、不横向溢出。

### 用户故事 3 - 自建发布可查看工具清单（优先级：P3）

作为把某个本体切片发布出去的负责人，我希望在自建发布卡片上点「查看工具」就能看到这次发布实际注册了哪些工具（名称、描述、参数），并明确知道这是发布时的快照，这样我不必去翻发布记录或重新发布才知道对外暴露了什么。

**优先级理由**：与固定发布对照，自建发布目前只在卡片上以“类型：X（N 个：a、b、c）”列出名字，看不到描述与参数；补齐后两块的工具查看体验才真正一致。该项依赖用户故事 2 的信息结构落位，故排在最后。

**独立验证**：对任意自建发布点「查看工具」，弹窗列出该发布的全部工具及其描述/参数，并标注快照语义；停机状态下点开，能明确看到失败原因而非空白清单。

**验收场景**：

1. **Given** 一个含 6 个工具的自建发布，**When** 点「查看工具」，**Then** 列出 6 条工具，每条含名称、描述与参数结构，数量与卡片显示一致。
2. **Given** 自建发布创建后本体发生变更，**When** 再次查看工具，**Then** 清单仍是发布时快照，且弹窗明确提示“需重新发布才会更新”。
3. **Given** 该发布容器已停止或记录缺失，**When** 点「查看工具」，**Then** 给出明确的失败说明，不得显示成“0 个工具”。
4. **Given** 工具数量较多（如 20 个），**When** 打开弹窗，**Then** 清单可滚动浏览，弹窗不遮挡关闭入口。

### 边界情况

- 业务系统 MCP 未在平台配置页登记时，仍应给出可参考的两段片段，并提示先登记；不得静默显示空内容。
- 平台外客户端与平台 Agent 的地址可达性相反：同一份片段在两处互不可用，弹窗必须靠标签与说明消除歧义，而不是让用户试错。
- 部署形态变化（固定服务未映射宿主端口、或平台 Agent 改为宿主直跑）时，两段中可能有一段不可用；此时必须如实说明，不得编造地址。
- 自建发布容器处于停机/容器缺失状态时，「查看工具」与「查看配置」的可用性需有明确区分（配置片段不依赖容器在线，工具清单依赖发布记录）。
- 自建发布的访问令牌属于凭据：卡片与片段沿用现有展示口径，不新增明文扩散面。
- 两个执行底座（本体函数执行服务、数据引擎执行服务）按 2026-10-19 决策已零工具化：都没有工具、没有协议端点，允许“无客户端配置片段”；这是唯一允许不出片段的类别。
- 工具清单为空（发布时未勾选任何工具）时，应显示“0 个工具”并说明原因，而不是报错。

## 需求 *（必填）*

### 功能需求

**配置展示（固定发布）**

- **FR-001**: 本体查询 MCP 服务、公共函数 MCP 服务、业务系统 MCP 三者的「查看配置」MUST 采用同一范式：一段宿主地址、一段容器内地址。
- **FR-002**: 两段内容 MUST 均为可直接粘贴的客户端连接配置片段，结构统一为「服务标识 → 连接配置」的映射形态（即 `{mcpServers: {<服务标识>: …}}`）。
- **FR-003**: 每条连接配置 MUST 包含连接类型标识与地址；连接类型取值 MUST 采用 MCP 客户端认可的值（Streamable HTTP / SSE），MUST NOT 使用自造值。
- **FR-004**: 第一段 MUST 使用宿主可达地址（含宿主端口），供平台外 MCP 客户端使用。
- **FR-005**: 第二段 MUST 使用容器内可达地址（容器名 + 容器内端口），供平台自身 Agent 挂载使用；两段 MUST 明确标注各自适用对象。
- **FR-006**: 业务系统 MCP 的「查看配置」MUST NOT 再展示平台内部存储条目；任何片段中 MUST NOT 出现平台管理字段（启用状态、业务数据标记、工具范围、内置标记等）。
- **FR-007**: 若该服务在平台配置中登记了鉴权请求头，片段 MUST 携带同样的请求头；未登记时 MUST NOT 生成请求头。
- **FR-008**: 三个服务的片段 MUST 使用同一命名口径的服务标识（稳定、可读、不随显示名变化）。
- **FR-009**: 服务尚未在平台配置页登记时（业务系统 MCP 场景），系统 MUST 仍给出参考片段，并提示需先登记该服务。
- **FR-010**: 宿主端口未暴露的内网执行底座（数据引擎执行服务）MUST NOT 出现宿主地址段，也 MUST NOT 生成客户端连接片段（零工具、无协议端点）。
- **FR-011**: 零工具且无协议端点的服务（本体函数执行服务）MUST NOT 生成客户端连接片段，MUST 仅说明其内网执行端点与调用入口。

**卡片结构（自建发布）**

- **FR-012**: 自建发布卡片 MUST 与固定发布卡片采用一致的信息层级与字段集合：服务标识 → 运行状态 → 端点 → 传输模式 → 可用工具（数量 + 查看入口）→ 角色/类型说明 → 操作按钮。
- **FR-013**: 自建发布的领域必要信息 MUST 保留并可辨认：发布类型与已选工具、所属本体、访问令牌、依赖的执行服务、工具清单为发布时快照的提示。
- **FR-014**: 自建发布卡片 MUST 提供「查看工具」入口，展示该发布实际注册的工具清单（名称、描述、参数结构）。
- **FR-015**: 工具清单 MUST 标注“发布时快照”，并提示本体变更后需重新发布才会更新。
- **FR-016**: 工具清单读取失败（容器停机、记录缺失、请求异常）MUST 以明确错误说明呈现，MUST NOT 以空清单或“0 个工具”冒充成功。
- **FR-017**: 两块区域的刷新入口 MUST 保持区块级单一入口；启停、创建、删除的操作语义 MUST NOT 因本次统一而变化。
- **FR-018**: 全部新增或变更的界面文案 MUST 为中文，并沿用既有术语（宿主地址 / 容器内地址 / 传输模式 / 发布时快照 / 自建发布 / 固定发布）。

### 关键实体

- **固定服务声明**：一个平台内置服务的展示与连接信息——显示名、稳定标识、角色说明、暴露面（对外/内网）、传输模式、宿主端点、容器内端点。它是卡片与两段片段的唯一事实源。
- **客户端配置片段**：一段可粘贴的连接配置——服务标识、连接类型、地址、（可选）请求头。不含任何平台管理语义。
- **自建发布服务**：一次按本体切片的动态发布——名称、发布类型、所属本体、已选工具、宿主端口、传输模式、访问令牌、容器状态。
- **工具清单条目**：一个对外工具的可展示声明——名称、描述、参数结构。固定服务的清单来自运行中服务，自建发布的清单来自发布时冻结的快照。

## 成功标准 *（必填）*

### 可衡量结果

- **SC-001**: 三个对外固定服务的「查看配置」在部署环境上 100% 给出两段片段，且每段可分别被外部客户端、平台配置页直接粘贴成功，无需手工改写任何字段。
- **SC-002**: 抽查三个服务 × 两段共 6 份片段，平台管理字段出现次数为 0。
- **SC-003**: 地址混用导致的配置失败从“需一次失败试错才能发现”降为 0 次——弹窗内 100% 的片段都带有适用对象标注。
- **SC-004**: 固定发布与自建发布卡片的信息项按清单逐项比对，除各自领域必要差异项外一致率 100%。
- **SC-005**: 任意自建发布的工具清单可在 2 次点击内查看完整内容（名称/描述/参数），100% 附带快照说明。
- **SC-006**: 卡片信息项增加后，在 1280×800 及以上的常见桌面视口下 100% 卡片内容完整可读，无横向溢出与按钮错位。

## 假设

- 沿用现有部署拓扑：本体查询（8002）、公共函数（8007）、业务系统（8004）暴露宿主端口；数据引擎执行（8005）、本体函数执行（8006）仅容器内可达。
- 固定服务不带鉴权令牌，只有自建发布强制令牌；因此固定服务的片段通常不含请求头，仅当配置页显式登记时才携带。
- 「查看配置」的定位是“提供可粘贴的连接信息”，平台管理字段的编辑入口仍留在「MCP 配置」页，不迁入弹窗。
- 自建发布的工具清单以平台侧发布记录为权威（发布时冻结），不依赖运行中容器的实时探测。
- 两段式标签沿用自建发布现有措辞（平台外 AI 客户端 / 本平台 Agent·容器内地址），避免同类信息出现两套说法。
- 本次改动仅涉及展示层与信息获取口径，不改变 MCP 协议端点、执行链路、发布与启停行为。
- 界面与文档一律中文；术语沿用项目既有词汇（“发布 = 对外声明 MCP 工具”等）。
- 数据引擎执行服务已按 2026-10-19 决策零工具化（`transport=none`，行为对外只经自建发布），因此与本体函数执行服务一样不提供任何连接片段，仅说明内网执行端点。
