# Optonto 本体开发平台 —— 技术框架与功能框架评估

> 评估日期：2026-08-26　|　评估范围：全仓库（frontend / core-backend / agent-backend / business-backend / mcp / .data / docker-compose）

---

## 1. 项目定位

Optonto 是一个**本体驱动（Ontology-Driven）的智能体开发平台**：用户以"场景 → 本体"两级结构，用可视化设计器定义领域本体（概念、关系、行为、规则、函数、业务流程），平台据此自动生成技能文件（SKILL.md），并由多 Agent 运行时把自然语言任务**规划成对本体行为/函数的结构化调用**并执行。

一句话概括：**把"业务知识"建模为本体，把"业务操作"抽象为行为，把"任务执行"交给受本体约束的多 Agent 编排**。

        │ /api 等               │ /agent-api (SSE 流式)

### 2.2 服务清单

| 服务 | 技术栈 | 端口 | 职责 |
|---|---|---|---|
| optonto-nginx | nginx:alpine 独立入口容器 | 81 | 全站唯一对外端口，反代三条路径（/、/api、/agent-api），全部 resolver 运行时再解析 |
| optonto-frontend | Next.js + React + TypeScript + antd + Tailwind（黑色科技风）+ ECharts + CodeMirror（纯 Node，不对外） | 3000(内部) | 全部页面 |
| optonto-core-backend | Python 3.12 + FastAPI + Pydantic | 8001 | 本体设计面 API：概念/关系/行为/规则/函数/流程/技能/需求对话/LLM 生成/SQL 生成/文件浏览/线程持久化 |
| optonto-mcp | Python（Starlette + MCP SDK，SSE 常驻） | 8002 | MCP 工具协议面：本体相关工具、本体函数、公共函数等 |
| optonto-agent-backend | Node.js + TypeScript（自研编排，非 langchain） | 8003 | Agent 运行面：父 Agent 规划、子 Agent 执行、校验管道、白名单、确认、记忆 |
| optonto-business-backend | Java + Spring Boot | 8080 | 业务数据源 API（行为 HTTP 接口的落地端之一） |
| optonto-mysql | MySQL 8.0 | 3307→3306 | 行为（SQL 类型）与业务数据持久化 |

**编排模式**：docker-compose 单网络 `optonto-net`，`.data` 与 `config` 目录卷挂载进容器（yaml 改动即时生效），MySQL 数据走命名卷。

### 2.3 存储体系（四类数据，四种载体）

| 数据 | 载体 | 位置 |
|---|---|---|
| 本体定义（概念/关系/行为/规则/函数/流程） | **YAML 文件（单一事实源）** | `.data/onto_market/{场景}/{本体}/ontology.yaml` |
| 技能文件 | Markdown | `.../skills/{技能名}/SKILL.md` + `meta.json` |
| 对话/线程 | JSON 文件 | `.data/threads/`（agent 端）、本体目录下 `threads/` |
| 业务数据 | MySQL | 行为接口读写 |
| 模型与密钥配置 | yaml + .env（不入库） | `config/config.yaml`、`config/.env` |

**评价**：YAML 作为本体单一事实源是本项目最重要的架构决策——可读、可 diff、Git 友好、设计器与文件浏览双向同步（CodeMirror 编辑器直接改 yaml 即时生效）。代价是放弃了数据库的事务/并发能力（见 §5 风险）。

### 2.4 关键技术决策

1. **设计面与运行面分离**：core-backend（Python/FastAPI，重 IO 与 LLM 生成）与 agent-backend（TS，重流式编排与状态机）拆成两个服务，各自独立演进、独立测试。
2. **MCP 作为工具协议**：行为执行、函数调用统一走 MCP SSE Server，Agent 端按"白名单"动态挂载工具，天然支持外部 MCP 工具混入（第三数据源）。
3. **SSE 全链路流式**：父 Agent 叙事（narrative，折叠块）与正文 token 分流；规划提交（submit_plan）后叙事定格，执行记录（exec_entry）逐条推送。
4. **mtime 缓存**：本体数据、MCP 函数列表按文件修改时间失效，避免每次规划全量重读。
5. **nginx 独立入口 + 运行时再解析**：nginx 拆为独立容器（2026-08-26），三条反代路径全部 resolver + 变量 proxy_pass，根治下游容器重启导致的 502。

## 3. 功能框架

### 3.1 功能全景

```
OPTONTO 本体市场（首页 :81）
├─ 场景管理（新建/删除需输名二次确认，删场景须空）
├─ 本体卡片（名称/介绍/概念·关系·属性·行为·规则计数）
│
├─ 本体设计器（design 页）
│  ├─ 概念：属性表格 + 属性约束（唯一/非空/枚举/匹配模式/取值范围 min·max）
│  ├─ 关系：基数(1:1/1:N/N:1/N:M) + 关联概念属性（source_attr/target_attr join 键）
│  ├─ 行为：HTTP/SQL 接口映射 + 参数/返回结构 JSON + op_type(command=写/query=读)
│  │        + 关联概念 + 接口测试
│  ├─ 规则：三分类（验证/推理/其他）
│  │        · 验证/推理 → 结构化规则设计器（对象/对象集/函数 + 9 操作符 DSL）
│  │        · 关联行为/关联函数声明
│  │        · 数据补充：保存时按规则结构引用概念自动推导 query 行为（剔主行为）
│  │        · 设计器选项收窄：函数限关联函数；概念限关联行为概念 ∪ 一阶邻居
│  ├─ 函数：本体函数（关联概念，可规划）+ 公共函数（统计/聚合等纯计算）
│  ├─ 业务流程：步骤化流程定义（供视图高亮与 Agent 参考）
│  └─ 文件浏览：ontology.yaml 的 CodeMirror 直编，双向同步
│
├─ 本体视图：ECharts 力导向图，概念/行为/规则/关系四类节点，
│            点击概念看属性与一阶关系高亮，流程高亮
│
├─ 需求对话（ConversationChat）：本体需求拷问模式（有限拷问、可开关），
│            分析结果沉淀、导出需求文档
│
├─ 技能管理：LLM 按模板生成 SKILL.md（0本体信息/1概念详情/2概念关系/
│            3属性及约束/4业务流程/5行为），frontmatter 硬校验，格式错误不落盘
│
└─ 智能体对话（运行面）
   ├─ 父 Agent：加载 SKILL 上下文 → 流式规划 → submit_plan（子任务 DAG）
   ├─ 规划硬校验管道（见 §3.2）
   ├─ 安全确认：写操作（command）强制人工确认弹窗，可"本对话默认执行"
   ├─ 子 Agent：白名单工具（主行为 + 规则数据补充行为 + 规则/父声明函数）
   ├─ 函数子任务：直连 MCP 执行，无 LLM 无确认（纯计算）
   ├─ 波次反馈：depends_on 分波执行，失败/结果回灌父 Agent 重规划（seq 防碰撞）
   └─ 执行记录：子任务/工具调用/确认分组展示，最终总结回流对话
```

### 3.2 校验体系（本项目最精耕的部分，分层分工）

| 层 | 时机 | 内容 | 策略 |
|---|---|---|---|
| 父 Agent 规划期 | submit_plan 后 | 结构（DAG/拓扑/悬空依赖/自环）、seq 冲突（含冒名已执行 seq）、行为名/函数名合法性、必填参数、**枚举/匹配模式** | 枚举/pattern → **统一 nudge LLM 自修一次**，复验不过才失败 |
| 父 Agent 规划期 | 同上 | **取值范围 min/max（仅 number/integer）** | **硬中断**（fatalReason 直通用户，不给 LLM 自修）——唯一硬停例外 |
| 子 Agent 执行期 | 每次 executeOntoBehavior | 必填参数（按 behavior_name 查表，覆盖所有行为） | 缺必填即报错，**不做**枚举/pattern/范围 |
| core 端 | 行为落地 | jsonschema 类型校验 | 类型兜底，错误回子 Agent 重试 |

约束的**单一事实源**是概念属性上的 `constraint`（yaml），经 `buildAttrConstraintMap → mergeAttrConstraints` 回溯合并进行为/函数的参数声明树，再递归校验（数组项/对象属性逐层，错误带路径）。改名参数（参数名≠属性名）按既定边界静默跳过，宁可漏检不可误拦。

### 3.3 数据补充与规则的关系图导航

规则的"数据补充"声明了校验该规则还需哪些**只读（query）行为**的数据。推导逻辑（2026-08-25 终版）：规则结构（rule_detail）实际引用的概念 → 关联这些概念的 query 行为 → 剔除主行为，保存时自动写入。子 Agent 白名单 = 主行为 + 数据补充行为 + （规则 ∪ 父声明）函数，即**最小权限运行时**。

## 4. 技术框架评价（亮点）

1. **架构分层干净**：设计面 / 运行面 / 协议面 / 数据面四分离，各自技术栈适配职责（Python 做 LLM 生成与胶水，TS 做流式状态机，Java 做业务数据源），是教科书级的"用对的工具做对的事"。
2. **YAML 单一事实源 + 双向同步**：设计器、文件浏览、LLM 生成、Agent 加载四处读写同一份 yaml，配合 mtime 缓存，既保证一致性又不失性能。
3. **硬校验管道是核心壁垒**：`plan-validation`（结构/拓扑/seq/名称/参数）+ `param-contract`（约束回溯）把"LLM 规划的不可靠性"收敛为确定性校验，197+ vitest 单测覆盖边界（数字字符串、单边范围、嵌套数组路径、seq 冒名等），这是多数 Agent Demo 与生产系统的分水岭。
4. **校验策略有明确的治理哲学**：枚举/pattern 软修、范围硬停、子端只查必填、类型 core 兜底——每条规则都有拍板记录，避免了"处处硬停"的体验灾难和"处处放任"的数据灾难两个极端。
5. **白名单最小权限**：子 Agent 只能看到主行为 + 规则声明的补充行为与函数，函数节点绕过 LLM 直连 MCP——既安全又省 token。
6. **工程化测试矩阵**：vitest 单测 + tsc 类型门禁 + Python urllib 零依赖 E2E（SSE 逐字节断言、自动批准确认弹窗）+ docker 全栈，测试资产可复跑。
7. **SSE 事件协议设计细腻**：narrative/token/confirm/plan_confirm/exec_entry/wave feedback 类型齐备，前端折叠叙事与正文分离，交互完成度高。

## 5. 风险与改进建议

| # | 风险 | 说明 | 建议 |
|---|---|---|---|
| 1 | **core-backend 无 pytest 覆盖** | 设计面 API（18 个 router）靠手工验证，回归风险随功能增长放大 | 优先给 schemas 校验与 skills/rules 生成链路补 pytest |
| 2 | **YAML 存储无并发控制** | 多人同时编辑同一本体 / 设计器与文件浏览并发写，存在丢更新窗口 | 加文件锁或 ETag（mtime 比对）乐观锁；多人协作是迟早的需求 |
| 3 | **跨端契约手写同步** | core 的 Pydantic schemas 与 agent 的 `types.ts` 是两份手写契约（如 constraint 的 min/max 两端各加一次） | 中期可引入 schema 导出（JSON Schema → TS 类型生成）或契约测试 |
| 4 | **前端大组件复杂度** | RuleTable 等行内编辑表格承载了大量派生逻辑（选项收窄/推导/警告），单文件偏厚 | 抽 hooks（如 useRuleDesign、useSupplements），逻辑下沉到纯函数便于单测 |
| 5 | **安全确认为进程内存态** | "本对话默认执行"信任仅存活于进程，重启即失效；权限体系（admin/operator/viewer + 本体域）设计已定未实施 | 按已确认方案推进记忆+权限落地 |
| 6 | **LLM 生成质量靠 prompt+硬校验** | 技能/本体/SQL 生成无自动回归，模型升级可能劣化输出 | 建立小型 golden-set 回归（固定 yaml → 生成 → 结构断言） |
| 7 | **business-backend 角色边缘化** | 目前仅是行为 HTTP 落地端之一，与设计面/运行面无深层联动 | 明确其定位：要么下沉为纯数据源，要么承接业务侧鉴权/审计 |
| 8 | **文档与代码不同步风险** | readme.md 描述的早期设计（langchain/langgraph、8010 端口等）已与现状偏离 | 以本文档为基准刷新 readme |

## 6. 结语

Optonto 已经越过了"Agent Demo"阶段，进入了**有治理、有校验、有测试的本体驱动 Agent 平台**阶段。它最突出的工程气质是：**所有 LLM 的不确定出口，都被一层确定性的结构校验接住**——规划有硬校验管道，约束有单一事实源，执行有白名单，生成有格式硬校验。当前的短板集中在设计面的测试覆盖、存储并发与跨端契约治理上，均为可预期的工程债，不涉架构返工。
