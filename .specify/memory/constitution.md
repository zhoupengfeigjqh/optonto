# OPTONTO 项目章程

## 核心原则

### I. 前端组件化与代码质量

- 组件命名 MUST 使用 PascalCase，文件名与组件名保持一致；Follow 项目既有技术风格
  （Next.js App Router + TypeScript + Tailwind），并遵循对应框架的官方推荐风格。
- 单个组件文件 MUST 不超过 500 行；超出 MUST 拆分为子组件或自定义 Hook。
- 组件的 props/状态类型 MUST 显式声明；MUST NOT 使用 `any` 逃逸，确需时 MUST 说明理由。
- 组件 MUST 保持单一职责，展示与业务逻辑分离（逻辑下沉至 Hook / 服务层）。
- 严禁在渲染路径中执行昂贵计算（大数组排序过滤、深拷贝、正则回溯、同步 I/O 等）；
  此类计算 MUST 移出渲染路径（`useMemo` / 派生数据层 / 服务端）。

**Rationale**：组件边界清晰、职责单一、渲染轻量，是前端可测试、可维护、可演进的前提。

### II. 后端分层架构与代码质量

- 后端 MUST 采用分层架构：接口层（路由/控制器）—业务层（领域逻辑）—数据访问层（存储/外部集成）。
- 每一层职责 MUST 单一；MUST NOT 跨层调用（接口层不得直连数据访问层；业务层不得依赖 HTTP
  请求/响应对象）。
- 接口层 MUST NOT 直接 import 数据访问层（`repositories`）或任何存储原语（文件读写 / 路径拼接 /
  mtime 等），MUST 经业务层（`services`）暴露的领域函数完成读写。
- 模块间 MUST NOT 引用对方的下划线私有符号（`_foo`）；需要跨模块复用的能力 MUST 提升为公开 API。
- Python 服务 MUST 遵循 PEP 8 与项目既有服务模式；Java 服务 MUST 遵循 Spring Boot 官方约定。
- 单个文件 MUST 不超过 500 行；超出 MUST 按职责拆分模块。
- 跨服务调用 MUST 通过显式契约（MCP 工具 / REST）进行，MUST NOT 依赖对方私有 API 或内部实现。

**Rationale**：分层与禁止跨层是控制耦合、保证可替换与可测试性的硬约束。

### III. 测试强制覆盖（不可协商）

- 前端：每个组件 MUST 有对应单元测试；用例 MUST 覆盖属性传递、事件触发、边界条件
  （空值、极值、异常输入）；核心逻辑行覆盖率 MUST 不低于 80%。
- 后端：每个接口（端点）MUST 有集成测试；用例 MUST 覆盖正常、异常、边界三类条件；
  核心单元覆盖率 MUST 不低于 80%。
- 测试 MUST 可在本地与 CI 以单条命令复现；不确定因素（时间、随机数、外部网络）MUST 打桩或注入。
- LLM 调用相关断言 MUST NOT 依赖真实模型输出（MUST 打桩或契约化）；真实模型调用仅允许出现在
  显式标注的 E2E 脚本中。
- 覆盖率未达标的变更 MUST NOT 合并，除非在计划中记录豁免理由与补测期限。
- 禁止编写无断言或以提升数字为目的的“占位测试”。

**Rationale**：覆盖率与用例维度是质量门禁的客观依据；打桩保证测试确定性与可复现性。

### IV. 无障碍与交互体验

- 所有可交互组件 MUST 支持键盘导航（Tab / Enter / Space / Esc 至少可用），焦点可见且顺序合理。
- MUST 遵循 WAI-ARIA：优先使用语义化标签；自定义组件 MUST 补齐 `role` / `aria-*` 与可访问名称。
- 交互反馈（点击、输入、导航等本地可判定结果）延迟 MUST 不大于 100ms；
  例外：LLM 大模型调用及其链路等待，此类 MUST 提供加载态或流式反馈。
- 异步操作 MUST 提供加载、成功、失败三态反馈；严禁无反馈的静默等待。

**Rationale**：无障碍是可用性底线；明确的反馈时限与三态约定避免用户面对“卡住”的不确定感。

### V. 性能标准

- 前端：单个组件首次渲染 MUST 不超过 100ms（生产构建、基准数据下测量）；渲染路径按要求
  禁止昂贵计算（见原则 I）。
- 后端：接口 P95 响应时间 MUST 低于 200ms（不含 LLM 调用与外部长耗时集成；此类 MUST 异步化
  或显式声明超时与降级策略）。
- 数据库查询 MUST 有支撑索引；新增查询 MUST 附执行计划或索引说明。
- 严禁 N+1 查询；批量场景 MUST 使用批量查询、联表或预取。
- 性能敏感变更 MUST 在计划阶段声明度量方式与性能预算，并在实现后给出实测数据。

**Rationale**：可度量的性能预算是防止体验与容量无声劣化的唯一手段。

### VI. 数据一致性与接口契约

- 所有涉及状态变更的操作 MUST 使用事务；MUST NOT 部分提交。
- 并发操作 MUST 考虑锁机制（悲观锁 / 乐观锁 / 唯一约束 / 幂等键），并在计划中说明所选策略。
- 可重试的写操作 MUST 具备幂等语义（幂等键或状态机），禁止重复执行造成副作用。
- 接口 MUST 遵循 REST 规范：资源化路径、正确的 HTTP 方法与状态码。
- 错误响应 MUST 统一格式（稳定错误码 + 可读 message），前后端 MUST 按同一格式解析。
- 业务失败 MUST 以领域异常（`errors.DomainError` 及其子类）表达，由全局处理器统一映射状态码；
  接口层 MUST NOT 自行发明状态码语义（`HTTPException` 仅限框架级 / 路由匹配类场景）。
- 上游或运行时底座的操作失败 MUST NOT 以 2xx + 失败体（如 `{running:false}`）掩盖；
  失败 MUST 以错误表达（「本就无操作」或幂等成功除外）。
- 对外契约 MUST NOT 写入无消费者的字段（"写而不读"的死键）。
- 所有端点 MUST 有接口文档；接口契约 MUST 与前端共享同一契约来源；
  契约变更 MUST 同步更新双方实现与文档。

**Rationale**：一致性与契约是分布式协作的正确性基础，接口不一致是前后端缺陷的主要来源。

## 技术治理与依赖管控

- 前端与后端 MUST NOT 引入非必要的第三方库。
- 引入任何新依赖 MUST 在计划（plan）中说明选型理由：所要解决的问题、被评估的替代方案、
  体积/性能与安全影响、维护活跃度；未说明理由的依赖变更 MUST NOT 合并。
- 优先使用标准库与既有依赖；若平台既有能力可实现，MUST NOT 新增依赖。
- 依赖版本 MUST 锁定（提交锁文件）；新增依赖 MUST 通过许可证兼容性检查。
- 跨服务共用的契约（转发目标 / 错误码 / 字段口径等）MUST 单点收口为**一份实现**，两侧共用；
  MUST NOT 各写一份副本——副本必然漂移，且漂移是静默故障。

## 开发工作流与质量门禁

- 所有项目文档（章程、规范 spec、计划 plan、任务 tasks、清单 checklist、评审记录）
  MUST 一律使用中文。
- 开发 MUST 遵循 Spec Kit 流程：specify → plan → tasks → implement；
  计划中 MUST 包含 Constitution Check，逐条声明对本章程的符合性。
- 合并前 MUST 全部通过：前端类型检查与单元测试、后端单元与集成测试、前后端契约一致性核对；
  任一未通过 MUST NOT 合并。
- 代码评审 MUST 逐条核对本文件原则；违反项 MUST 记录理由、影响面与整改计划。
- 契约变更 MUST 由先改的一方同步另一侧实现与接口文档，确保前后端一致。

### 测试组织与命名（2026-10-05 补充）

- 测试文件 MUST 与被测源文件**同目录**（co-located），MUST NOT 另建 `tests/` 平行树。
  理由：① 同名约定自解释，无需维护「哪个测试对应哪个源文件」的映射；
  ② 源文件被删除时测试随之删除，MUST NOT 留下孤儿测试；
  ③ 隔离由**构建链路**保证而非目录位置——生产构建 MUST NOT 产出测试代码
  （后端 `tsconfig` 的 `exclude` + 镜像只复制编译产物；前端只复制 `.next/standalone`）。
- 命名 MUST 为 `<被测模块>.test.ts` / `.test.tsx`（前端组件用 `.tsx`）。
- 被测模块超 500 行而按关注点拆分测试时，MUST 用 `<被测模块>.<关注点>.test.ts`
  （如 `agent-factory.visibility.test.ts`），MUST NOT 用无语义的通名（如 `a.test.ts`）。
- **测试代码 MUST 与生产代码同等对待**：MUST 纳入类型检查（后端 `tsconfig.test.json`），
  MUST NOT 因「只是测试」而豁免类型与规范。
- 新增/抽取的**核心逻辑模块** MUST 同时补齐单测并纳入覆盖率门禁的 `include`；
  抽出的模块若未进门禁，MUST NOT 计入「已拆分」的完成度——
  否则会出现「拆出是为了可测，却因漏配门禁而从未被测」的空转。
- 覆盖率门禁 MUST 有配置文件与阈值；只有脚本而无配置的覆盖率命令视为无效门禁。

## 治理

- 本文件 MUST 优先于其他一切开发实践；发生冲突时以本文件为准。
- 修订程序：任何修订 MUST 以文档形式提出（动机、影响面、迁移计划），
  经项目维护者评审通过后方可合并生效。
- 版本策略（语义化版本）：
  - MAJOR：不兼容的治理规则或原则的删除、重定义。
  - MINOR：新增原则/章节，或对既有指导的实质性扩充。
  - PATCH：措辞澄清、错别字、非语义性细化。
- 合规审查：每次 plan 与 PR MUST 执行 Constitution Check；
  不一致 MUST 显式记录并获得批准，禁止默认豁免。
- 运行时指导：spec / plan / tasks 等模板在运行时读取本文件，本文件为唯一权威来源，
  MUST NOT 在模板层复制原则内容。
